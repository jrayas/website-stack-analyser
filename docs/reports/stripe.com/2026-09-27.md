# Stripe

## Site Overview
- **URL:** https://stripe.com
- **Access date:** 2026-09-27
- **Pages examined:** `https://stripe.com` (redirects to locale path `https://stripe.com/au` based on geo-IP), response headers for `https://stripe.com`, `robots.txt`, rendered HTML of the `/au` homepage (scripts, meta tags, `__NEXT_DATA__`).
- **Limitations:** Analysis is limited to public, unauthenticated HTTP requests (curl/WebFetch) against the marketing homepage and robots.txt. No JavaScript execution/browser rendering was performed beyond parsing the server-delivered HTML, so client-side-only behaviour (e.g. further hydration, XHR/GraphQL calls made after load) was not observed directly. Stripe's actual payments backend, databases, and internal services are not visible from the public site and are explicitly out of scope.

## Evidence and Uncertainties

- **Strongest evidence:**
  - The `__NEXT_DATA__` script tag and hashed `buildId` value in the homepage HTML are direct, high-confidence evidence of Next.js.
  - The extensive Content-Security-Policy header returned with the initial `307` redirect response is a rich, direct source of first-party and third-party domain allow-lists (Contentful, Stripe's own CDN/analytics subdomains, `increment.com`), all cited above.
  - Custom response headers (`X-Stripe-Proxy-Response`, `X-Stripe-Server-Rpc-Duration-Micros`, `X-Wc`) indicate a bespoke internal edge/proxy layer rather than a generic off-the-shelf hosting header signature.
- **Direct observations vs deductions:**
  - Direct observations: presence of `__NEXT_DATA__`, CSP domain lists, response headers, self-hosted font filenames, asset path prefixes.
  - Deductions: that Contentful is used as the marketing-site CMS is inferred from CSP allow-listing of Contentful's app/asset domains, not from a visible admin UI or exposed content API; the exact rendering strategy (pure SSR vs ISR/SSG) is inferred from the `mkt-ssr-statics` naming convention, not confirmed by inspecting cache headers per-page.
- **Unresolved questions:**
  - What backend/API framework powers Stripe's actual payments platform (this cannot be observed from the public marketing site — it is architecturally and likely organisationally separate from the marketing pages analysed here).
  - Exact Next.js version and React version — would require access to a source map, package.json, or an exposed `/_next/static/BUILD_ID` style version marker that includes semver.
  - Whether Tailwind CSS or another utility framework is used — would require inspecting compiled class names or a CSS source map, which was not done in this pass.
  - Whether Contentful is used for all marketing content or only specific sections — would require probing more pages/locales for consistent Contentful CDN asset usage.

## Recreation Guidance

- **Recommended minimal dependency set (recommendation, not confirmed fact about Stripe's stack):** Next.js (latest stable) with React, a headless CMS such as Contentful (to match the observed integration) or any equivalent headless CMS, self-hosted web fonts, a CDN/edge layer (e.g. Cloudflare, Fastly, or a custom nginx reverse proxy) in front of static assets, and Stripe.js loaded client-side if payment collection needs to be replicated.
- **Version constraints:** None can be verified from public evidence; use current stable Next.js/React releases unless further evidence (source maps, package manifests) becomes available.
- **Unknowns to investigate before implementation:** Confirm Next.js/React versions via any exposed build manifest; confirm whether a CSS-in-JS or utility-CSS approach is used by inspecting class-name patterns in rendered markup; determine whether the marketing site and the core payments dashboard share a codebase (unlikely, but unconfirmed).
